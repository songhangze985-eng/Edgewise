# 研究事件可靠投递：实现与验收方案

本文件记录现状和后续工程方案。带稳定 ID 的客户端事件已支持重复确认和内容冲突检测。跨库中断仍需人工核对与恢复。研究测量定义仍以研究负责人确认的方案为准。

## 已确认的故障边界

- 批次响应逐条标明接收、重复、拒绝或未确认。客户端删除已确认和明确拒绝的条目，保留待确认的条目。
- 事件先写 Redis Stream，再写 Mongo，随后才执行指标推导和问卷触发。带稳定 ID 的事件会在写入 Redis 后记录原始 Stream ID。跨库写入和后续副作用各自提交，旧事件缺少稳定 ID 时仍可能重复写入。
- 在隔离的 `FakeRedis` 中向 Mongo 写入注入异常后，已实际观察到 Redis Stream 中仍留有一条事件。该检查只证明这一失败窗口存在，不代表覆盖其他中断位置。
- 同一业务动作可能由前端和服务端分别报告；即使网络重试去重，也不能因此推断跨来源事件是同一动作。历史队列没有稳定事件 ID，历史重复也不能可靠地自动合并。

## 建议的改造顺序

1. 带稳定 ID 的事件使用 MongoDB 回执原子占用。同一用户重试相同内容会复用已确认的事件 ID，重复 ID 配不同内容会被拒绝。旧事件可能没有 ID，无法可靠识别历史重复。
2. 中断后的回执会保持处理中，服务端返回未确认并保留客户端事件。新回执使用 Redis 脚本同时写入 Stream 条目和短期幂等记录。若 Mongo 回执尚未记录事件编号，24 小时内可凭 Redis 记录找回原编号；过期后保持未确认。Mongo 回执已记录编号时，重试可补写原事件，即使 Redis 条目已丢失。原始事件保存后、指标推导开始前中断时，重试可以继续推导。指标推导完成后、问卷触发开始前中断时，重试将从问卷触发继续。管理员可从存储状态接口查看超过五分钟的未确认回执和所在阶段。旧版写入阶段，以及已经开始但未确认的指标推导或问卷触发，仍需人工核查。
3. 先确定一个持久化事件账本作为事实来源，并用唯一键保证并发写入同一 ID 只产生一条记录。Redis Stream 可作为可重建的投递或索引层；Mongo 和 Redis 之间没有天然的跨库事务，不能靠先写某一边就宣称完全可靠。确认本地 JSON 降级是否允许该保证；不能保证时应明确返回失败或只作为开发模式。
4. 为推导和问卷触发建立可恢复的处理状态，分别跟踪完成情况和错误；处理中断后可重试。每个副作用需要独立满足幂等，特别是计数、推荐奖励、问卷入队和外部调用；仅给原始事件加唯一键，或先标记已处理再执行副作用，都会造成漏算或重复。处理状态与副作用应在同一事务中提交，或使用可重建投影与可验证的去重键；跨存储场景需明确失败恢复方式。

   问卷队列由 MongoDB 保存，入队和移除在并发时按版本合并。题目保留最早的到期时间。首次更新会读取旧 Redis 队列，迁移程序不能覆盖新版队列。若在队列已保存、记录 `survey.enqueued` 前中断，题目仍可下发，入队事件可能缺失。

   首次看反馈、首次看报告、报告停留或重访的待入队记录与计数在 MongoDB 中原子保存。第二次练习触发核对当前同意周期内本人名下两条不同的已完成练习会话，排除研究后测，并和待入队记录原子保存这两个会话编号。若入队前中断，后续拉取待答问卷时会沿用原定时间补入队。旧实现已经入队的练习题保留原状态。

   问卷 A 的练习次数、首次完成时间和七天回访次数由当前同意周期的会话记录重算。原始事件仍可保留多个来源的同一会话记录。管理页和采集面板导出在缺少会话证据时将这些指标置空。七天窗口未结束时，回访次数置空并给出窗口状态及结束时间。历史原值仍可供内部核对。

   问卷 A 的事件计数按 MongoDB 当前值原子递增。对应题号、产品指标和来源元信息一起保存，并发处理不同事件时不会覆盖彼此的增量。对于只有一次原子计数更新的新版事件，后续计数在替换来源前会把已有凭据留在原回执。重试可凭原回执或仍匹配的来源跳过已完成的推导。没有凭据的旧回执，以及包含其他副作用的推导中断，仍需核查。

   问卷 B 新客户端提交时发送下发编号、账号和同意周期。后端校验题目是否在下发清单中，同一次下发只接受一份提交，并逐题保存回执。切换账号或重新同意后，前端关闭旧弹窗，后端拒绝携带旧身份或旧周期的提交。已确认的题目重试时复用结果，尚未开始的题目可继续。若答卷和回执编号已一起保存，重试可以补确认回执。缺少对应答卷证据的处理中回执仍需核查。旧客户端使用原提交编号，或继续按原接口提交。

   问卷展示回执必须与同一账号、同一同意周期、同一版本及同一组题目的下发记录匹配，才计入管理统计。旧客户端没有下发编号的回执保留为原始事件。浏览器回执可说明界面上报了展示，无法确认参与者实际看到了题目。

   已核验的展示回执会一次保存该批题目的展示标记。若保存过程中断，可以用原事件编号重试，不会新增原始事件或重复计入展示人数。统计优先读取持久化标记，旧缓存迁移只补缺失字段。

   24 小时内最多下发两次问卷。下发额度在 MongoDB 原子占用，并读取仍在有效期内的旧记录，因此并发拉取和 Redis 缓存丢失都不会重置额度。额度占用后请求中断时，该次额度仍有效。

   第七天问卷的展示和提交都核对当前同意周期内的后测完成时间。历史周期的后测和旧缓存中的 `J1` 不能解锁当前题目。重新同意后是否安排新一轮后测仍由研究方案决定。

   第七天后测按账号在 MongoDB 原子登记提交。会话保存后若中断，当前同意周期内的相同答卷重试会沿用原会话，补齐索引、盲评任务和指标，再标记完成。已确认的答卷重试会直接返回该会话。管理员可通过 `/api/v1/system/storage-status` 的 `posttest_submission_receipts` 查看五分钟后仍未确认的后测汇总。该汇总区分会话可恢复、会话未确认和同意周期已失效，省略账号及答卷内容。若在会话保存前中断，仍需核查。
5. 为积压、永久拒绝、冲突、失败重试和无法重放的旧记录提供可观测信息。撤回同意后的队列、已存事件及重放权限必须遵循最终同意书和数据保留规则；不应悄悄把撤回前后事件当作同一状态处理。

## 验收场景

- 单用户连续重试、并发重复提交、重启客户端和响应丢失后重试：同一事件原始记录一份，相关指标与问卷副作用各执行一次；不同用户使用相同 ID 不互相影响。
- 批次混合有效、无效、未同意、重复、冲突和暂时失败事件：结果逐条可追踪，队列仅移除已明确处理的项目；不能因为一个项目失败而丢弃其余项目。
- 在每个存储和处理步骤前后注入进程退出、Mongo/Redis 断线和恢复，检查原始记录、处理状态、计数和问卷队列最终一致；对无法保证的情况明确暴露并保留修复依据。
- 验证旧客户端、旧离线队列、Redis 冷恢复、用户切换、同意撤回与重放；历史事件无稳定 ID 时不制造无法证实的去重结果。
- 使用隔离数据库和浏览器验证真实请求及导出，并检查事件标识、处理状态和错误可审计；测试须覆盖并发和故障注入，而非只检查正常成功响应。
